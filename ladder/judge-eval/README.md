# Recorded judge evaluation

Source idea: [How the Claude Code team thinks about verification](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/), 2026-11-16.

34 original recorded questions, with facts, image paths, byte hashes, one-sentence keys and oracle references. No oracle outcomes or answer keys are added to the model input. Categories map Important -> must-fix, Nit -> nit, Pre-existing -> pre-existing. All 34 are JUDGE/FLOW/PRODUCT; REVIEW severity is exercised by the golden journey.

6 MUST_CATCH / 8 MUST_NOT_FLAG / 20 CONTROL. The target of eight defensible MUST_CATCH cases is NOT met: ambiguous UI/oracle mismatches were excluded. The six positives cover one failure family (SQLite connection closure), not six independent kinds of bug. Their server source matches the oracle copy exactly after newline normalization. Recorded source establishes unclosed connections; the later oracle records a Windows database-handle cleanup failure, but does not establish which handle caused that failure. These are limited regression cases, not causal proof of that oracle failure.

The counts above describe the original set. The judgeEval2 extension adds 10 cases: 3 MUST_CATCH, 3 CONTROL, 3 EVIDENCE_GAP and 1 CODE_QUALITY. There are now 25 tune and 19 holdout cases. Four of the 10 additions go to holdout. Whole-run partitioning keeps sibling judgments in the same partition. Similar code across runs remains a possible leakage source. The original `manifest.json` documents the historical set. See [report-tune-2arm.md](report-tune-2arm.md) for the extension's provenance and results.

`python eval.py tune.jsonl --arm control --dry` validates recorded provenance, images, strict schemas, examples and native rendering without providers. `--arm prompts2` explicitly enables the trial for that process. Both arms replay the same facts, targets, owners and images through `providers.render_question`. The evaluator keeps the recorded folded JUDGE schema, which is keyed by subject, and rebuilds ordinary questions with the current shared builders. `SELDON_SOURCE` can select a different Seldon `src` directory. The CLI accepts only this directory's tune set, including in dry mode.

`python eval.py tune.jsonl --arm control --run-dir C:/seldon/tests/judgeEval2-2 --output C:/seldon/tests/judgeEval2-2/summary.md` illustrates the native Codex invocation. Use a fresh `judgeEval2-<n>` directory for each authorized batch. The default model is gpt-6.1-terra at medium effort. The runner invokes each distinct recorded question once per arm, with up to three concurrent calls. Multiple scored cases can share a folded answer. The runner uses an isolated temporary `CODEX_HOME` and retains the native receipts in the batch directory. It uses no model grading or retries. No `.env` files are read.

Recall requires a must-fix finding that matches a MUST_CATCH key by meaning. A CONTROL false alarm is a must-fix finding in its scope, which can be one subject of a folded decision. MUST_NOT_FLAG remains a separate historical negative class in the paired report. CODE_QUALITY is graded separately for an explicit actionable maintainability finding, with severity recorded. EVIDENCE_GAP covers absent runtime observations or an oracle assertion that the supplied evidence cannot substantiate. These cases are outside recall and false-alarm denominators. Offline summaries accept `--arm ARM --results PATH --grades PATH` with explicit semantic adjudications. Read coverage alongside all rates.

An authorized real run is one development measurement; it establishes neither holdout quality nor product acceptance.
