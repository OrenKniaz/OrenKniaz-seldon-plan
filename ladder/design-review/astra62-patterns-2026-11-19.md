## Recurring patterns, their owners and the smallest cuts

### 1. The planner commits the builder to a test implementation before there is a product

**Design mismatch in Lead.** `lead.propose` asks for runnable argv at B. `lead.check_set` appends the builder's checks to those commands, deduplicates by argv and the entire milestone promise list, and assigns that list to each check. This makes a proposed method effectively irrevocable, while a link to every promise says little about which action a check observed. Lead C13 gives the builder implementation and checks. C28 requires an approved what/how/test spec. Lead blueprint §§1–2 separately assign proof obligations, executable checks and independent replay.

- lf03 reached B after five plan/review rounds. At r108–110 the runner tried to start a browser-console expression, `location.href` and `document.title` as programs. The builder's headless file-URL check passed at r111. Seven candidates failed integrated proof. lf04 r70/r80–84 shows that even a correct diagnosis and a working replacement did not dislodge the old command.
- lh03 r101–105 passed the greeting and invalid-argument assertions, then failed the walkthrough because the documented rejection of `--help` exited 2. This one came from the builder's walkthrough. A visitor command with an expected error and a test process reporting success have different exit contracts. Orchestrator q04/q05 similarly wrote and passed a CSV check that never read the export as the intended consumer would.

**Replace** the executable portion of Lead's pre-build CHECK with the promised action, exact observable result and linked promise. Retain any invocation the person actually specified as part of the product. After B the builder supplies an unattended check for that action, including assertions for expected errors. Seldon exercises it independently. Delete the plan-argv union and blanket promise assignment in `lead.py`. Retain the accepted witness outside later builders' control, replay it on each candidate, and independently review a replacement against the original obligation so weakening a test cannot erase a regression. **FOR OREN**. Make the B boundary explicit in Lead blueprint §2 when changing the approved test representation. The owner still approves what/how/test before coding under C28.

### 2. Recovery gives the next turn to someone who cannot change the failed input

**Routing bug in both shapes, amplified by design.** Orchestrator both4QB made 196 PRODUCT calls out of 242. After the guide changed, seven subjects repeatedly received oversized evidence. Across rounds 2–10, 189 requests were rejected before a verdict. New thread IDs and four scripted approvals let the same candidate cycle (T-239, productLoop). Batch 3 q01/q02 then spent 37/39 calls in a different loop. WORK had supplied gaps, COACH asked for the missing question, and the simulator acknowledged it (T-251). The workerQuestionLoop patch protects exact repeated receipts. Its report leaves paraphrased recurrence open.

Lead lf04's retained endpoint has 108 started calls, including 53 WORK and 52 COACH, one COACH without a result. Of 53 failure records, 21 contain integrated proof failing on the launcher and 32 concern a missing question. The handover's 106 was an earlier count. In lh05 the planner requested a fresh checkout pinned to the prior candidate at r92. Editing the product made that SHA historical at once (r116/r150). A scripted “try” supplied another turn. It conferred no ability to change an approved command or the proof runner's checkout.

**Simplify** `lead.fail/build`, `decisions.coach/decide` and the corresponding unit route around the existing durable obligation and failure record (I5/I6, R7/R15/R17, Lead C16/C18). Deliver the builder a reproducible product defect, the planner a plan correction, and the proof owner a runner or evidence defect. Preserve the original observation alongside any reply. lf04's next WORK r72 carried direction but lost the exact failure. Remove the repeated generic BUILD coaching branch. After the prescribed repair and steering, keep the same actionable question or pause until its named input changes. Explicit retry stays available for a transient fault. A receipt's wording, a fresh session ID and a simulator acknowledgement are poor evidence that the input changed.

### 3. The proof runner knows facts the judge guesses, and the judge can bless facts nobody witnessed

**Shared evidence design with different failure policies.** `proof.observe` owns the commit, clean checkout, command, exit, cleanup and artifacts. Orchestrator's guideCommand fix exposes checkout provenance in `judgment.py`. Lead's independent `lead.judge` renderer omits that context and treats every uncertain finding as builder rework. At lh05 r52 the judge saw command, commit and streams, but no runner checkout fact. At lf02 r172 it wanted to see the desktop window opened by the guide despite a separate headless observation. Running a launcher alone cannot establish which controls worked. A file-URL browser journey can, and preserves Foundation's direct-from-disk promise.

lf02 provides a direct check on the judge. At r76 it asked the builder to supply a missing browser helper. Git tree `ce7d5327` already contained `checks/kit/browser.cjs`. At r65 the documented Node check used the helper and passed. `lead.judge` excluded that path from its source view while decoding committed PNGs as text. Its r70 prompt was 734,220 bytes. At r140 the same false repair resurfaced on `e9524f1c`, which also contained the helper. Give the judge the candidate file inventory and the relevant text or images in their proper form.

In the other direction, nine of ten Orchestrator B-arm scripted Cs explicitly carried incomplete guide verification. All five ShelfLife judge packets already contained the favicon error. Batch 3 marked eight products verified, including the two with malformed CSV. Quiet Bench Stop replays measured from a persisted zero cursor, which cannot establish progress *after acknowledgement*. The guide oracle also passed a PowerShell variable literally where the documented shell expands it. Those last two findings require different dispositions (guideCommand, firstPathProof, census-batch3, ab-triage).

**Keep** `proof.observe`, isolated Git execution, independent semantic judgment and browserProof's phase/URL/error diagnostics. **Replace** duplicated checkout explanations and projections in `judgment.py` and `lead.py` with one runner-owned account of candidate, actual action, result and artifacts per promise. Pass those facts to both judges. Keep a guide step unobserved if its actual action was skipped. Separate product failure, missing observation and unavailable environment at the existing proof/decision boundary (C14/C15/C26, R9/R12). A missing core witness needs proof or owner-approved scope revision. A permitted minor limitation stays visible at C. Keep quietDesktop's noninteractive Git defaults for the separate editor bug. The scripted quietDesktop gate did not exercise native proof launching.

### 4. Repeated translations lose the user's words and make models reconstruct facts already in the store

**Design overhead, strongest in Orchestrator.** T-236 was an implementation bug. Reusing edit positions as trace IDs stranded features from an executed wave. T-237/T-238 then normalized citation spans, aliases and derivable sole ownership across roughly 30 refusal sites (+141 source lines in refuseSweep). T-245 hid the CSV direction in history while the dedicated check-in fact was null. T-246 treated a continuing owner's narrower scope as a competing writer. Batch 3 had zero refusals and all three delivered Quiet Bench slots reached wave 2. Those fixes moved a real boundary.

The same loss affects products. The plannerBrief trial preserved “Expiring soon” in the user-words appendix but omitted it from the assignment in sb01/03/05. The trials-off batch missed it in four of five products. Combined trials improved Foundation's median longest line from 379 to 100 with 35/35 browser checks in both arms. ShelfLife's median longest line fell from 3,467 to 602 while its raw failures rose from zero to 18. Fifteen were three console assertions observing one favicon 404 in each product. Three were genuine literal misses. The A/B changed two switches and the single-arm probes do not isolate the heading cause (codeShape, plannerBrief, trialFidelity, ab-triage).

**Simplify** the inputs to `questions.py`, `architecture.py` and `plan.py` before adding more normalization. Code supplies the approved owner's ID, scoped paths, prior check-in and applicable verbatim constraints from their existing records. The planner supplies the assignment and makes genuinely ambiguous ownership decisions. Remove requests to echo uniquely derivable fields and then remove their alias/refusal branches. Consolidate duplicate WORK/guide rendering as trials are decided. Preserve actual scope enforcement, which correctly rejected product-local evidence in guideEvidenceScope's s05/q03. Preserve the independent review that caught ShelfLife s05's missing persistent edit. C9/I1/I6, R4/R6/R12/R16/R19 support these cuts.

### 5. A lane often proves the message arrived, while the ladder asks whether the product works

**Development evidence mismatch.** firstPathProof proved the generated WORK prompt contained coaching. trialFidelity explicitly proved the position of the heading in provider input. leadThin's 151-case gate proved scripted delivery and detection of a weakened prior test. Each is a valid regression check for its boundary. None samples how a native builder and judge respond to a new dream. Conversely, nextWave's native replay reached the requested wave on the first reply and batch 3 recorded no such refusal. That is evidence for retaining a targeted fix.

**Change the exit evidence, without adding product code.** Keep a lane eligible to land on its focused evidence. Close the fault class only when the original user-visible failure disappears on the integrated candidate and the neighboring product promises still work (blueprint P2–P5/P9/P10). Source is now 7,614 lines of tracked Python/CommonJS at `4263505`. Count deletion of redundant responsibilities, with LOC as a cross-check. A shorter product file or a greener gate has no intrinsic bearing on delivered behavior.

## What the two shapes tell us

Lead removes Orchestrator's area/contract/wave handoffs and still stalls on a greeting. Those handoffs explain a subset of failures. The common problem is who owns the promise, its executable demonstration and the decision after it fails. Orchestrator's clean hello/Foundation batch and the useful independent catches argue for retaining its one-owner path and its multi-owner machinery where a real interface needs it. Lead lacks evidence on the two harder dreams. Making Lead compulsory for micro would change C27. Bypassing Orchestrator's machine by size would also change C5/R1. Both are **FOR OREN** decisions. These cohorts support neither.

## How to tell whether the cut worked

1. Freeze one integrated SHA, trial settings, briefs, runtime, model, effort and scripted decisions. Run the same four dreams in each chosen shape with a paired plain-agent build under the same conditions and independent scorer. First require the lf03/lf04 headless witness to replace the failed implementation while still detecting an incorrect message on the same file-URL journey. Then run five slots per dream and shape. Report every slot, including starts without a product. Keep larger dreams parked.
2. Score the delivered user path on the final candidate. Hello needs exact output, streams and invalid-argument status. Open Foundation by file URL and exercise all three independent controls headlessly. Check ShelfLife's literal heading, clean console and persistent edit. In Quiet Bench observe the actual cursor at Stop acknowledgement, bound subsequent work, reopen saved data and consume a rectangular CSV. Run the guide's real shell steps. Exact Node 20 stays unverified until exercised there.
3. For each slot record scripted C, owner acceptance, verification completeness and independent pass/fail/unverified separately. Inspect every disagreement against the same candidate. Report observed Seldon bugs, ordinary product defects caught and repaired, environment limits and checker errors separately. Zero Seldon bugs includes false verification, needless escalation, desktop openings and repeat dispatch without changed input. A genuine repair that restores the product is evidence the loop helped.
4. Report first-pass and final product results, extra WORK/COACH/judge calls per unresolved obligation, worst slot as well as median wall time and fresh tokens, and maintainer judgments blind to arm. Pair plain-agent scores before claiming an advantage. Five clean slots per cell show the failure did not recur in that sample. They do not establish a zero underlying defect rate.
