# Seldon UI design, 2026-11-12 (completes Fable's mockup)

Mockup: `ui-mockup-2026-11-12.html` (self-contained, open from disk). Binding: Charter C20 (chat acts, one read-only page shows, built for the host app's browser pane), Blueprint §3 (unit states, waves, flow review). Host facts: `inapp-ui-research-2026-11-12.md`.

## Decisions
1. Two surfaces, no overlap. Chat decides (gates, size, pause, resume, stop). The page only shows; its controls only navigate, filter or change the view. Every chat reply ends with a `Page` link to the exact anchor.
2. One page, two widths, same DOM. Narrow (host pane, about 360-560 px) is one column; at 980 px or more (container query) it becomes three reading columns. `⤢` asks the host to open it full screen.
3. Four layers top to bottom: header (dream, rail ALIGN to C, state, Next, Why, a "waiting for you" band) → Now (changes since you looked, active beads) → Waves (waves / kanban / timeline) → Trace, Evidence, Plan, Not judged.
4. Unit states are Blueprint §3 exactly. `WAITING` is shown inside READY as a dashed card with its reason, because "queued, and why" (C12) is the main thing a user asks about.
5. Honesty labels stay visible: "not judged", "scripted yes, not owner acceptance", "fresh same-provider call", "M1 stand-in".

## Chat surface (MCP tools; every tool returns plain text, under 60 s)
| Tool | Input | Output |
|---|---|---|
| `seldon_start` | `vision` (user's words), `folder` | run id, then Gate A text |
| `seldon_status` | `run?`, `wait_seconds?` (≤50; returns on the next change) | status block below, or the pending gate text if one is open |
| `seldon_answer` | `words` (user's reply, unchanged) | what Seldon understood ("approve", "change: ...", "not now"), then next step |
| `seldon_control` | `action` pause, resume or stop; `confirm?` | pause/resume: new state. stop: kept/lost preview; stops only with `confirm=true` |
| `seldon_inspect` | `subject` (unit, worker, check, requirement or contract id) | six lines: What, Why, Needs, Now, Proof, Who + Page link |

Status reply (exact shape, at most 10 lines):
```
SELDON  <dream> · <size> · wave <n> of <m> · <STATE> · <elapsed>
  done <n> · working <n> · waiting <n> · need a look <n>
  <glyph> <unit> <title> <STATE> <time in state> <worker/provider>   (one line per active unit, then attention units)
  ◌ <unit> <title> <wait reason>                                     (queued, at most 3, then "+N more")
Next  <next step>
Why   <reason>
You   nothing needed | Gate X is waiting: <one line>
Page  http://127.0.0.1:<port>/#now
```
Gates. The chat agent relays the text unchanged and passes the reply to `seldon_answer`. Seldon, not the agent, reads it. Each ends with `Answer in your own words:` and a `Page` link.
- A (Vision Lock): I understood, Size (say "size small" to change), I would add, In, Out, Bar, Unknowns. Replies: approve · change ... · not now. Link `#plan`.
- B (plan): counts, wave 1 units with order, Proof rule, Review with its independence label, Changed in review. Large dreams: areas and contracts, then the wave outline, then wave 1 in detail. Replies: approve · change ... · not now. Link `#plan`.
- Check-in (each wave): Built, Proven, Bumps, Next. Replies: continue · change ... · pause. Link `#waves`.
- C (acceptance): Try it, Built, Trace, Stubs, Bar, Not judged, Demo. Replies: accept · change ... · not now. Link `#evidence`.

Pause: running sessions finish and hold before integration, nothing new starts; reply lists each unit's fate and what is kept. Stop: always two steps. The first call changes nothing and returns `kept / lost / later "resume <dream>"`. Only the user's "stop, yes" sends `confirm=true`. Anything else cancels.
Inspect: "what is u004 doing and why" → `seldon_inspect(u004)`. Seldon never looks inside a worker session (R8), so "Now" is the state, the time in it and the last event.
Optional extras per host, each also works without it:
- Claude Code: status line script reads `state.js` (line 1 of status); elicitation form for gates (choice approve/change/not now + note); the gate stays pending in Seldon if the form is dismissed.
- Copilot in VS Code: elicitation form; MCP App iframe of the same page (experimental).
- Codex, Copilot CLI: text only; elicitation if the host declares it.

## Page views
- Header (sticky): rail with gates in bold, state, wave n of m, elapsed time, Next and Why, the you-band when a gate is waiting, anchor tabs (Not judged shows a count).
- Since you last looked: the events after the viewer's last "seen" (kept in the browser only; it changes nothing in the run).
- Active beads: one card per running unit, attention units first. Each card shows glyph, id, title, STATE, time in state, what it is doing (wait reason or state meaning), why (its requirements), last event, step pips, worker, provider, attempt, area, wave. Below: "Queued, and why", one row per unit with its wait reason and time queued.
- Waves (default): one card per wave with goal, status and a `now` chip on the current one. Unit dots and integrated count, with attention units named in orange. Step strip EXECUTE → WAVE-VERIFY → FLOW REVIEW → STEER → CHECK-IN. The current wave lists its units; other waves fold to "▸ N units". Then "After this" (next wave), and outlined waves drawn dashed.
- Kanban: columns READY, WORKING, PROVING, JUDGING, INTEGRATING, DONE. Each column says who acts (code, worker, LLM judge). Empty columns fold to a 30 px rail. REWORK / FAILED / BLOCKED lanes sit above the flow; when all three are empty they collapse to one line. Cards show id, title, time in state (commit when DONE), reason, worker and attempt, area, wave, ▲ provided and ▽ consumed contracts (orange when the contract is being corrected). Narrow: lanes stack, columns scroll sideways with snap, and count chips jump to a column. Full screen: the six columns share the width and the three lanes sit side by side. DONE shows the newest 8.
- Timeline: one bar per unit, coloured by state, with gate diamonds on the run row.
- Trace and inspector: tree feature → requirement → check (RED/GREEN at commit) → unit → commit, with the evidence state of each requirement. Picking any unit anywhere opens the six-line inspector. That is the same text `seldon_inspect` returns.
- Evidence: screenshots (lightbox), flow verdicts, unit judgments, check runs newest first.
- Plan: Vision Lock (improvements, In, Out, quality bar with verdicts), contracts with provider → consumers and stale marks, decisions and discoveries.
- Not judged: everything that is neither passed nor failed, with the reason. The footer shows calls, reworks and integrated units.
- Live update: static files served on 127.0.0.1. Seldon's loop rewrites `state.js` (the projection, the same shape as the mockup data) after each transition. The page reloads it every 2 s and keeps scroll and selection. The live dot turns red when the file is older than 10 s while a run is active. There is no write path.

## What M1 can fill now vs later
- M1 now: header, rail, state, Next and Why, gates; active beads with worker, time in state and wait reasons (dependencies, scope held); kanban; timeline; trace; check runs; unit verdicts; screenshots; Not judged; one wave. The M1 stand-ins (DEMO/PRODUCT judgment in place of flow review, contract text on requirements) are labelled on the page.
- M2: Area, Contract and Decision records (real contract badges, stale marks, the Plan contracts list), the skeleton wave, flow verdicts, fixup units as cards.
- M3: several waves (wave cards, `now`, After this, outlined waves), STEER and check-in, unit steering (BLOCKED or FAILED with the planner's action), handoff notes.
- M4 (front door per Blueprint): the five MCP tools above, `wait_seconds`, per-host extras. Until then, M1 runs report through the dev runner and the page is the only live view.

## Open questions for Oren

2. Should kanban rows be grouped by wave (swimlanes) for dreams of 50+ units, or is the wave badge enough?
3. Is FAILED its own state (recoveries spent), or does such a unit always go straight to BLOCKED under unit steering? The Blueprint table lists neither, so the page treats both as lanes.
4. Is the stop flow ("stop", then "stop, yes") right, or should stop always need a typed run name?
5. Should "since you last looked" ever leave the browser (for example a `seldon_status` line "N changes since you last asked")?
