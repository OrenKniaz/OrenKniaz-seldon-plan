# Research notes for the blueprint, 2026-11-11

Sources: Cursor, "Scaling long-running autonomous coding" (cursor.com/blog/scaling-agents) and "Towards self-driving codebases" (cursor.com/blog/self-driving-codebases, second half read through a summary); AWS on DEV, "8 agents wrote perfect components and nothing worked". All self-reported or anecdotal.

## What supports the blueprint
- A planner, sub-planner and worker hierarchy built a browser (1M+ lines, about a week) and other 0.5-1.6M line projects. One long agent did not. Macro idea confirmed by someone else's scale run.
- A rigid cycle "bottlenecked by the slowest worker": matches R7, no global phases.
- A gate of full correctness before every commit stalled everything; they keep a periodic green snapshot with a fixup pass: matches unit-local proof plus WAVE-VERIFY.
- Eight agents each wrote correct components and 17 bugs sat at the seams (names, routes, formats, IDs). Fix: one shared contracts file given to every agent, then a review agent tracing user flows across boundaries: matches R4.
- Planner model differs from the best coding model: matches R13.
- Their v1 browser converged on an architecture "unfit to evolve", called a specification failure; verification of the result is weak (no correctness metric). These are Seldon's differentiators: Vision Lock, reviewed architecture, independent proof.

## What to fold in (proposed small edits, within the ratified shape)
1. Sub-planners. One planner gets tunnel vision on a large project. DETAIL should run per area (one planning call per area), not one planner for the whole wave. Fits R2 and R3; make it explicit in M2/M3.
2. Flow review at WAVE-VERIFY. Add a judge that traces each user flow across the contracts it crosses, on the integrated product. This is what found the seam bugs.
3. Name the fixup pass. A WAVE-VERIFY failure becomes a fixup unit owned by the failing scope; integration itself never waits on the whole suite.
4. Worker handoff carries notes, concerns, deviations and findings back to the planner that asked (our discoveries; C10, C16). Needed for steering in M3.
5. Prompts: constraints beat instructions ("no TODOs, no partial implementations"); concrete ranges beat "many". These are principles and belong in guides under R12.

`exec resume` (rework in the same session, R8), `fork` (start several workers from one session that already holds the architecture and contracts; worth testing in M2 to cut cold-start cost), `review`, `--output-schema`, `--image`.
