# Can Lead keep a promise across milestones?

## In ten lines

1. Lead remembers the first milestone’s code, approved plan and proof after a restart.
2. Its next builder gets the previous checkpoint and usability feedback, but must piece together what still has to work.
3. On the first candidate of milestone two, the guard is already asked to try every promise delivered so far.
4. A scripted greeting journey already catches a broken first milestone, even when the builder weakens its old check.
5. The clearest escape comes during repair. The guard can count something it saw before the latest code change as working now.
6. The final gate can therefore report full verification without a fresh observation of an earlier promise.
7. Keep one history for each approved promise, with the words the owner accepted and what happened on each candidate.
8. Walk every delivered promise on the candidate going forward. One trip through the product can prove several things.
9. Use the milestone check-in to shape the next brief, then regenerate the agenda and handover from the same history.
10. Try a two-step pantry upgrade with real saved stock. Losing a unit, or failing to look for it, must keep final acceptance closed.

## Where a regression gets through

**1. A repair can invalidate a perfectly good observation.** Suppose M2 candidate X preserves M1’s saved quantity but its shopping list is wrong. The builder fixes the list on Y and changes the shared load path. On Y the guard is explicitly asked to revisit failed and repair-affected subjects only. The verdict retains old actions for subjects it considers unaffected, including their original commit. The coverage calculation asks whether a handle occurs in the combined actions. It never asks whether that action ran on Y. If the ordinary checks miss the saved-data case, C sees passing check IDs and no limitation. Even `verification_complete=true` is reachable. The stale action is visible on inspection. This is a source-level counterexample, not an observed production incident. The golden `guard-repair` arm deliberately skips previously good actions and expects verified C. `judgment.py:42–58,78–92,107–115`, `lead.py:419–427`, `decisions.py:604–614`, `tests/seldon/test_journey.py:1852–1867,2040–2043`.

**2. The guard sees the plan’s translation of the promise.** For a modern plan, `obligations` returns the planner’s action/result/counterexample dict. The guard gets those dicts. The original story, constraint value and owner’s decision may be visible in the builder spec but absent from the guard question. A B line saying “saved rows reload” can be exercised on an empty installation that creates its own rows. The old customer’s rows still disappear on upgrade. A missing action becomes a limitation, which allows publication and a C request. A too-weak action linked to the handle may generate no limitation at all. Preserve the original meaning beside B’s test standard and require an actual outcome for each link. `lead.py:50–87,359–362,392–408`, `judgment.py:47–72,81–114`, `decisions.py:604–614`.

**3. A failed replay can lose its diagnosis.** If an old check fails and the guard supplies neither a repair nor an amendment, `lead.prove` tries to attach undefined `red`. The runner’s generic fault route gets the exception instead of the failed witness. Publication is still held. This is present on the reviewed SHA. T-287 records an earlier reproduction and a fix on a different candidate. `lead.py:392–412`, `run.py:309–325`, `ladder/TICKETS.json:3679–3688`.

**Existing proof to keep.** The two-milestone golden journey changes the greeting to “Broken, Ada!” and replaces its script with one that prints the expected answer. It checks for the retained failing M1 witness, a same-session M2 repair and a current successful replay. It also exercises a repeated failure that stays pending across reopen. Its normal reopen is at B. Neither that greeting nor a newly populated pantry exercises previously saved user data across an upgrade, handoff regeneration at M1 check-in, or a repair that introduces a second regression. `tests/seldon/test_journey.py:1556–1562,1700–1718,1947–1969,1979–2000,2027–2051`.

## Test dream — The pantry I already stocked

> Build me a little local pantry I can use in my browser. Give it to me in two usable milestones. In the first, let me add a named item with a whole-number quantity, use one, and see the amount left. If I try to use one at zero, explain why and leave it at zero. When I close and restart the app, every item and its exact quantity must still be there. Give me a short guide so I can try it myself.
>
> In the second, let me give an item a category and see a shopping list of exactly the items at zero, once each. A category is optional. Bring my existing pantry forward automatically, including items I never categorize. I want to keep using the same stock controls on the same page.

| Checkpoint | What a correct run shows |
|---|---|
| M1 published | Through the browser add Rice 3 and Tea 1. Use one of each. Try Tea once more. Restart. Read Rice 2 and Tea 0, with the zero-stock refusal observed. Record candidate H1, actual values, guard feedback and the fresh-copy guide. Preserve a copy of this **M1-created** data for the upgrade. |
| Check-in and reopen | Before replying, close the controller. With the rendered files missing, reopen on the same H1 and pending request. Both files regenerate with the same commitments, pending choice and next action. Give an in-scope direction such as “Put the optional category beside the existing stock controls.” The M2 brief quotes it, names H1, carries the quantities and usability observation, and keeps M1’s B lines. A previous waiver could cover a routine check-in; dropping uncategorized stock would still need a new owner decision. |
| M2 first candidate | Open a copy of that existing pantry under M2 without re-entry or reseeding. Categorize Rice and leave Tea uncategorized. After restart see Rice 2 and Tea 0; the shopping list contains Tea exactly once. Use Rice down to zero and exercise the refusal again. Both zero-stock items now appear once each. Repeat the fresh-copy guide separately where it promises a clean start. Attach candidate, per-promise results and screen-specific human feedback. |
| Discriminating repair | In the scripted journey make candidate X omit uncategorized Tea **from the shopping list only**. Have its repair Y fix the list but reset every positive quantity to one on upgrade. A fresh install and the shopping-list count can both look right on Y. The guard must explicitly see Rice 1 instead of 2 on the same M1 data, retain H1’s pass and X’s history, hold publication/C, quote the original B line and return Y’s reproduction to the same M2 builder. This is the case the greeting journey misses. |
| Final evidence | On repaired Z, start again from untouched M1 data, re-walk the full delivered set and show the guide, source/quality judgment and remaining limits. C can show full verification only when each due promise has a Z observation. A scripted C remains labelled. A subsequent authorized real run uses the same owner brief and observable checks; a clean first pass demonstrates preservation, while a repair claim needs an actually observed regression. |

The next unproven result is a real new builder taking over this saved pantry after check-in and a guard establishing the earlier and new promises together on the final candidate.
