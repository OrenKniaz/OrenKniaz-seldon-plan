## 1. The design in six sentences

1. **A wave is a row, not a mode.** The run loop repeats `DETAIL → REVIEW → EXECUTE → WAVE-VERIFY → FLOW-JUDGE → STEER → CHECK-IN` once per wave on the same code path; wave 1 is index 0 and only differs by B (R1).
2. **B approves an envelope, not a document.** The envelope is the accepted commitments (vision `scopeIn`, `improvements`, `quality` handles). Everything below it (areas, contracts, decisions, wave outline, units) is Seldon's to change through one recorded door, STEER. A change to the envelope goes to the user (C16, C21).
3. **STEER is the only replanning door.** Wave end, a unit that exhausted its recoveries, and the user's steering words all enter the same state, ask the same bounded question, and leave as typed amendments that code applies.
4. **Ownership follows the path, latest wave wins.** Scopes are exclusive only among units of one wave. The owner of a path is the latest unit whose scope holds it; checks, fixups and gaps route by path, so cross-wave overlap needs no special case (T-20).
5. **Judges are asked only about what changed.** A flow or quality verdict stays current while the git trees of its owners are unchanged (the existing `judgment.current`); accumulated checks rerun by code every wave. Judge calls per wave follow the wave's size, never the product's (R2, R7).
6. **VALIDATE is a code AND plus one question per accepted commitment**, fed verdict rows and behaviour, never source.
7. **One subject loop, one uncertain rule** (core review F2, F3). Flows, per-area quality and commitments are subjects of one judge loop; "uncertain, one re-ask, else not judged" lives once in `inference.call`. M3 lands on that base and ends with fewer run states than M2 has.

## 2. Run flow and states

```
ALIGN → A → ARCHITECT → ARCH-REVIEW → DETAIL(w0) → REVIEW → B
per wave: EXECUTE → WAVE-VERIFY → FLOW-JUDGE → STEER → CHECK-IN → DETAIL(w+1) → REVIEW → EXECUTE ...
last wave: CHECK-IN → VALIDATE → C
```

**Run table changes** (`states.py`), the whole list:

| State | Change |
|---|---|
| `STEER` | **New.** Entered by `FLOW-JUDGE.satisfied`, by `EXECUTE.stuck` (units FAILED after two recoveries, nothing else can progress) and by `CHECK-IN.revise` (user words). Exits: `steered → CHECK-IN`, `replan → DETAIL` (same wave, named areas only), `fail`. |
| `CHECK-IN` | Exits become `next → DETAIL`, `last → VALIDATE`, `revise → STEER`, `fail`. |
| `REVIEW` | Adds `reviewed-wave → EXECUTE` when B exists. `REPAIR` loses the "deferred to M3" refusal. |
| `EXECUTE` | Adds `stuck → STEER`. Failed units no longer end the run. |
| `VALIDATE` | Replaces `PRODUCT-JUDGE`. Same subject loop as `FLOW-JUDGE`, with commitments as subjects. |
| `FLOW-FACTS`, `PRODUCT-FACTS` | **Deleted** (F2). The re-ask is one inline call inside `inference.call` with a `more_facts` callback; a crash between the two calls repeats one question, which is cheaper than two states, `pendingJudge` and the `judge_uncertain` record. |

**Unit table:** one new terminal state `REPLACED` (`FAILED --replaced--> REPLACED`, `BLOCKED --unblocked--> WAITING`). A replaced unit's successors declare `replaces`; `plan.prerequisites` resolves a dependency on a replaced unit to its successors.

Net: one run state added, two deleted, one renamed; one unit state added. No DETAIL-NEXT, no WAVE-PLAN, no REPLAN state: they are DETAIL with a wave index and a list of areas.

## 3. Records: the smallest set

| Record | Kind | Content | Why it must exist |
|---|---|---|---|
| **WaveRow** | typed row, like `UnitRow` | `index, state(OPEN/CLOSED), goal, start, end, revision, authority, observed, verdicts, repairs, steer, checkin` | The wave-scoped fields on `RunRow` today (`finalCommit, finalObservations, demoVerdicts, requirementVerdicts, pendingJudge, checkin, repairs, waveStart`) move here; `pendingJudge`, `qualityVerdicts`, `productVerdict` are deleted. `observed` is one index per end commit, `{check: observation}` and `{unit: tree}`, built once by WAVE-VERIFY; `verdicts` is `{subject: ref}`. They replace the six per-subject scans of F1. `RunRow` shrinks to run-level truth plus `wave: int`. |
| **discovery** | exists; add `kind` | `kind: file / contract / scope`, `target` (a path, a contract handle from the brief, or text), `correction`, `unit`, `wave`, `disposition` | C10 typed amendments. Workers already return `discoveries`; the enum lets code route without reading meaning. |
| **steer** | new immutable record | the STEER answer: per discovery a disposition, a bounded list of amendments, the remaining wave outline, `why` | The single source for every post-B plan change (I6). |
| **envelope** | field on the approval record | commitment handles and texts the user last approved, plus the plan revision id shown | Replaces the whole-document equality in `run.py` and `judgment.refresh_units` (F1: B stores the plan three times and compares documents on every judge step). |

**Stable handles.** `plan.merge` renumbers `n001`/`u001` globally on every merge (T-72). In M3 code assigns `w<wave>.<area>.<position>` once, when that wave's area answer is merged, and never re-merges earlier waves. The plan document accumulates; each wave adds a revision. DONE units and their nodes are immutable history.

## 4. Planning: outline, then detail just in time

**ARCHITECT** stays one call. Its `waves` entry grows from `{goal}` to `{goal, commitments}`: each accepted commitment is closed in exactly one wave. Code checks the union equals the envelope (the structural half of "does this plan lead to the whole dream"). The list bound rises from 8 to 12; a user-dictated count ("10 waves, first…") is a kickoff fact.

**DETAIL(w)** is today's `detail.step` with three changes:
- It asks only the areas that have something to do in wave w: a commitment of this wave, a stale contract endpoint, an open placeholder, or a STEER correction. Other areas get no call.
- Each area brief carries, besides today's facts: this wave's goal and the area's commitments in it; **what exists here** (the area's DONE units, one row each: scope, requirement obligations, the worker's own summary line; at most 24 rows, beyond that the area must subdivide, which DETAIL already supports); existing check handles in the area; local `file` discoveries targeting the area; changed contracts as old text and new text.
- `Product in this area` (file listing capped at 64 with a count) stays. The worker, not the planner, reads source (C13, "planner never reads Seldon source" applies equally to the product).

**REVIEW(w)** is the existing per-area bounded review, run for the areas detailed in this wave; cached by basis as today. Three repairs per wave (counter on WaveRow); if a gap survives, the wave runs with the review labelled "gap not resolved" and the gap shown at the next check-in. Never a dead end after B.

**Skeleton (R5).** Wave 0 keeps its rule. An obligation now names the **commitment** it defers (a handle from the supplied list) instead of a requirement in its owner's own unit, so a later wave can close it. It closes when that commitment's VALIDATE verdict is satisfied; the area that owns the placeholder path sees it as a fact in every DETAIL until then.

## 5. What carries between waves

| Carried | Where it lives | Who reads it next wave |
|---|---|---|
| Product | git: `candidate`; wave w+1 `start` = wave w `end` | workers (worktree), PROVING (wave-start RED), WAVE-VERIFY |
| Checks | plan nodes with file paths; accumulate | WAVE-VERIFY runs all of them on the wave's end commit, hermetic (v1.6) |
| Contracts, decisions | the outline in the current plan revision; full text, never diffs | every DETAIL and WORK brief that touches them (agreed literals have this one carrier) |
| Discoveries | discovery records with disposition | `file` → the owning area's DETAIL or an owner fixup; `contract`, `scope` → STEER |
| Verdicts | unit, flow and quality verdict records keyed by owner git trees | reused while trees are unchanged; re-asked otherwise |
| Envelope | approval record | code gate before every EXECUTE; VALIDATE subjects |
| User's standing words | approval records (check-in policy, pins) | CHECK-IN |

Nothing is carried in a prompt, a summary document or a session. A fresh call gets a fresh slice (Blueprint §2).

## 6. STEER, CHECK-IN and replanning

### 6.1 STEER: one bounded question

Facts (code-built): wave goal; one row per unit of this wave (handle, area, state, verdict, summary line); the `contract` and `scope` discoveries, at most 24 (more: code splits by area into several STEER calls and merges; two amendments to one handle trigger one re-ask on that handle with both texts); failed units with their last failure; user words if any; the remaining outline; the envelope with handles.

Answer schema: `dispositions` (per discovery: `adopt / defer / reject`, reason); `amendments`, at most 12, each `{target: contract|decision|area|wave|commitment, action: add|change|drop, handle, text, sources}`; for each failed unit `{unit, move: resplit|change-approach|fix-contract|raise-scope, guidance}`; `outline` (remaining waves with commitments); `tell` (what the user should hear, including "we need something different").

**Code applies, normalising instead of refusing:** unknown handle on `add` gets a handle; a no-op amendment is dropped; an open commitment missing from the returned outline is appended to the last wave; a `commitment` amendment or a `raise-scope` move is never applied by code, it becomes a scope question for CHECK-IN; a contract `change` must carry the complete new text and stale-marks its consumer areas via `architecture.stale_consumers`; the result must pass the existing `architecture.outline` validator. One exact-fix re-ask, then the amendment that fails is recorded as rejected with its reason and shown at check-in. STEER never blocks a wave close.

**No question when there is nothing to decide:** no non-local discoveries, no failed unit, no user words and no remaining wave means the transition is code. Hello-world keeps today's call count without a size branch.

### 6.2 Unit steering (T-18)

When EXECUTE can no longer progress and units are FAILED, the run enters STEER inside the open wave. For `resplit / change-approach / fix-contract`, code marks the unit REPLACED and DETAIL re-asks only that unit's area with the guidance as a correction (the existing merge-correction path in `detail.ask`); successors join the same wave; BLOCKED dependants return to WAITING. **Bound:** one steering per failed lineage. If a successor also exhausts its recoveries, the question goes to the user at an immediate CHECK-IN with three honest choices: give guidance, drop the commitment (a recorded deviation, C21), stop.

### 6.3 CHECK-IN: a C-act in chat (C8, C17, C20)

Code composes the card from records, no LLM: wave goal and result; features with satisfied flows (and screenshots as page links); discoveries and what STEER did with each; amendments applied; scope questions, if any; the next wave's goal. The user answers in chat in their own words; the existing DECIDE call classifies `approve / revise / decline`. `revise` carries the words into STEER (§6.1), which may produce amendments, a scope change, or a reorder of waves; impact is computed by code (commitment → areas → outline entries → not-started units) and shown before the user confirms a scope change.

- A **scope change** (any envelope amendment) always waits for the user and records a new envelope on approval.
- Otherwise the check-in follows the user's standing policy (see §11 item 3): the user may say at B or at any check-in "do not stop again unless scope changes"; the card is still recorded and shown on the read-only page.
- Seam for T-21: when the `user` callable has no answer yet, `decisions.decide` returns without a transition and `Run.run()` returns the parked cursor with the lease released. The wait is the user's, costs nothing, and resumes by `reopen` (I5, C23).

### 6.4 Bounds on replanning, in one place

| Loop | Bound | Then |
|---|---|---|
| STEER answer invalid | 2 exact-fix retries (C4) + 1 re-ask | failing amendment rejected and shown |
| Unit lineage | 2 recoveries, 1 steering | user at check-in |
| REVIEW repairs | 3 per wave | run labelled, gap shown |
| Waves added by STEER | outline stays at most 12 open entries | further need is a scope question |
| Fixups after WAVE-VERIFY or flow gap | existing recovery count of the owner | unit steering |

## 7. Scope overlap across waves (T-20)

- **Areas** stay disjoint plan-wide; they are the stable partition and change only by a STEER `area` amendment.
- **Units** are disjoint within a wave (the scheduler's existing overlap wait stays as the runtime guard).
- `waves.owner(path)` = the latest non-REPLACED unit whose scope matches the path. `plan.traced_units`, `fixups.plan`, `fixups.handoff` and the check-owner rule (v1.6) call it. A wave-1 unit whose paths were all taken over is never reopened.
- **Inherited checks.** A unit that takes over a path inherits the checks stored there as `preserves`. It may change or delete an inherited check file only if its plan names that check handle under `revises`, traced to an amendment or a requirement of this wave. An undeclared change fails PROVING with the one fix named. Its unit JUDGE sees old and new check text for revised checks. This designs out "a later wave goes green by weakening an earlier wave's tests".
- **Verdict currency.** A superseded unit's verdict is history. C15's source check becomes: every commit folded into the candidate is a unit patch with its own unit JUDGE verdict (code reads integration records). `judgment.refresh_units` stops re-judging earlier-wave units whose scope tree moved because a later, judged unit wrote there. Needs ratified wording (§11 item 2).

## 8. Judges and proof at size

| Step | Who | Subject | Calls per wave | Size of one question |
|---|---|---|---|---|
| Unit JUDGE | LLM | one unit's diff and checks | units worked this wave | one unit (existing bound) |
| WAVE-VERIFY | code | every accumulated check on the end commit | 0 | n/a |
| Flow review | LLM | one feature's behaviour across its contracts | features whose owner trees or crossed contracts changed | one feature |
| Quality | LLM | one criterion **in one area**, behaviour only | (criterion, area) pairs whose area changed | one criterion's checks in one area |
| STEER | LLM | one wave: unit rows + non-local discoveries | 0 or 1 (split above 24) | one row per unit |
| VALIDATE | code AND, then LLM | one accepted commitment: its features' acceptance text and verdict rows, its walkthrough screenshots | once, at the end: commitments + guide | at most 12 feature rows |

- Quality moves from "one criterion over the whole product" (grows with every area, T-36) to per-area subjects judged in the wave phase beside flows; code ANDs them per criterion.
- VALIDATE's code half: every commitment has features; every feature a current satisfied (or visibly not judged) flow verdict; every requirement a green check on the final commit; no open placeholder; no REPLACED unit without successors; candidate equals the fold of judged patches. Its LLM half asks, per commitment, "is this promise delivered as accepted, or was it narrowed?" That is the check that catches a removed feature under green tests (C15).
- The guide unit is added by code to the last wave only. A VALIDATE gap opens a repair wave through STEER (C15), reported at the next check-in.
- **One loop (F3).** `subjects.step(store, provider, kinds)` serves FLOW-JUDGE (flows and per-area quality of this wave) and VALIDATE (commitments, guide): prune by tree currency, ask, gap to owner fixup, save, AND. `flow_review.step` and `judgment.step` collapse into it; briefs stay per kind. Subjects are asked in parallel under the run's capacity, as planning already is (F1: 100 serial features is hours).
- **Reads stay flat (F1), as a condition of every M3 lane:** `store.plan(revision)` cached by immutable revision id; no function scans all observations or all records of a kind per subject or per unit (use the WaveRow index; records carry `wave` and `unit` and are read by key); `plan.prerequisites` reads a per-revision map. J-A asserts it: store reads per unit in wave 5 no higher than in wave 1.
- Each run reports judge calls and largest question bytes per wave. **Design assertion to test:** the largest question in wave 5 is no larger than in wave 1.
- Known cost not solved in M3: WAVE-VERIFY reruns all checks every wave (code time, linear in checks). Acceptable for L3; if it hurts, reuse may key only on whole-tree ids (R9). T-32 (integration lock) stays open for hundreds of units.

## 15. Open risks, stated plainly

- The STEER schema is the one new place where an LLM writes structure; if real answers fight it, fix the schema or the facts (R12), and consider splitting "dispositions" from "outline" into two questions before adding prompt text.
